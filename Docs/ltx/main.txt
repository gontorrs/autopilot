Resumen

Autopilot es un sistema completamente autónomo de automatización de escritorio para Windows,
diseñado para permitir que usuarios con movilidad reducida puedan utilizar un ordenador exclusiva-
mente mediante interacción por voz. El sistema procesa una única instrucción hablada en lenguaje
natural y ejecuta de forma autónoma la tarea solicitada de principio a fin en el dispositivo local, sin
requerir intervención adicional del usuario, conexión a Internet ni transmisión externa de datos.
Esta solución ha sido diseñada siguiendo un enfoque neuro-simbólico que combina redes neuronales
profundas locales para el procesamiento del lenguaje y la percepción multimodal, junto con plan-
ificación automatizada. En primer lugar, un modelo local de reconocimiento de voz transcribe la
instrucción del usuario; posteriormente, un modelo de lenguaje de gran tamaño identifica la inten-
ción del usuario y extrae los parámetros correspondientes a la tarea. Un planificador determinista
genera un plan de acciones, garantizando una ejecución determinista y explicable de la tarea. De-
spués, varios agentes especializados de visión-lenguaje interactúan con los elementos de la interfaz
gráfica mediante grounding visual y entradas convencionales de ratón y teclado. Finalmente, un
agente de verificación confirma la correcta finalización de la tarea sin supervisión humana. Todo
el procesamiento y la inferencia se ejecutan localmente en el dispositivo del usuario, garantizando
privacidad total de los datos y funcionamiento sin conexión.
La solución ha sido evaluada utilizando siete plantillas de tareas en 21 ejecuciones experimentales y
comparada con otros cuatro enfoques alternativos de automatización de escritorio. Autopilot alcanza
una tasa de éxito del 100 % en las tareas, con cero fallos de planificación y cero exposición de datos,
superando a todas las alternativas evaluadas en términos de autonomía, precisión de ejecución y
preservación de la privacidad.


Palabras clave: Inteligencia Artificial, modelos de voz a texto, modelos de visión-lenguaje, planificación
     automática, automatización de escritorio, accesibilidad.

Abstract

Autopilot is a fully autonomous desktop automation system for Windows designed to enable users
with limited motor function to operate a computer exclusively through voice interaction. The system
processes a single free-form spoken command and autonomously executes the requested task end-to-
end on the local device, without requiring further user intervention, internet connectivity, or external
data transmission.
This solution has been designed following a neuro-symbolic approach that combines local Deep
Neural Networks for language processing, and multimodal perception, and Automated Planning for
reasoning, A local speech recognition model first transcribes the user command, after which a large
language model identifies the user intent and extracts the corresponding task parameters. A deter-
ministic planner generates a plan of actions, ensuring deterministic and explainable task execution.
Subsequently, some specialised vision-language agents interact with graphical user interface ele-
ments through visual grounding and conventional mouse and keyboard inputs. A final verification
agent confirms successful task completion without human supervision. All processing and inference
are executed locally on the user’s device, ensuring complete data privacy and offline operation
The solution has been evaluated using seven task templates across 21 experimental runs and com-
pared against four alternative desktop automation approaches. Autopilot achieves a 100% task suc-
cess rate with zero planning failures and zero data exposure, outperforming all evaluated alternatives
in terms of autonomy, execution accuracy, and privacy preservation.


Keywords: Artificial Intelligence, Speech to Text Models, Vision-Language Models, Automated Plan-
    ning, Desktop Automation, Accessibility

Chapter 1

Introduction

Artificial intelligence is changing the way users can interact with digital environments. Traditional
human-computer interaction relies on explicit physical input through devices such as keyboards,
mice, touch screens, or predefined voice commands. Current voice-based tools already address part
of this need. For example, Windows Voice Access allows users to control Windows through spoken
commands, but it is based on a fixed command vocabulary and generally requires the user to guide
the computer step by step. This helps in hands-free interaction, but the user still has to perform most
of the planning effort.
Other recent systems, such as autonomous cloud-based agents, can interpret free-form natural lan-
guage and execute multi-step tasks with less guidance. However, they usually depend on remote
inference, which implies transmitting screenshots, file names, task descriptions, or intermediate in-
formation to external servers. They also tend to operate reactively, observing the screen, choosing
the next action, executing it, and repeating the process, instead of generating a complete and repro-
ducible plan before execution.
Recent advances in Speech Recognition, Language Understanding, Visual Perception, and Auto-
mated Planning make it possible to move beyond these limitations. Instead of only mapping spoken
phrases to predefined commands or relying on remote reactive agents, a system can allow the user
to describe an intention and then reason locally about how to execute it. This form of interaction is
complex because a computer desktop is not a structured environment by default. The system must
transform real screen information, such as windows, icons, text fields, buttons, and changing visual
states, into a simplified representation that can be interpreted by artificial intelligence models. It
must also convert a human request into a sequence of actions that is not only executable, but also
understandable, repeatable, and explainable.
In this context, the problem addressed by this project is the autonomous control of a personal com-
puter through spoken natural language. This problem is relevant not only for accessibility scenarios,
but also for situations in which users cannot or do not want to interact with a keyboard and mouse
step by step. Examples include temporary physical constraints, multitasking contexts, repetitive
desktop workflows, or environments where hands-free interaction is more convenient than direct
manipulation.
Autopilot is a fully autonomous desktop automation system for Windows that accepts a single spoken

natural language command and executes the described task without any further human interaction.
The system operates entirely on the local device without transmitting any data off the device. Its ar-
chitecture combines a deterministic automated planner with local Vision Language Models (VLMs)
and Large Language Models (LLMs), forming a neuro-symbolic pipeline that is evaluated against
four alternative systems across performance, reliability, and privacy metrics.


1.1     Problem description

The general challenge is to transform an open spoken request into a correct sequence of desktop
actions. A user should be able to describe the desired outcome in natural language instead of issuing
one rigid command per interface step. For this to work, the system must understand the intention,
extract the necessary task parameters, perceive the current graphical interface, decide which actions
are required, execute them, and verify whether the result has been achieved.
This general challenge becomes more specific in the Windows desktop environment. The system
must interact with conventional graphical applications through the same interface available to a
human user, without relying on privileged application APIs or cloud services. This requirement is
especially important when working with private files, local applications, or unstable internet connec-
tivity. It also makes the system useful for accessibility, since users with reduced motor function may
benefit from operating the computer through a single spoken instruction rather than a long sequence
of manual actions.
Autopilot addresses these limitations by accepting a single free-form voice prompt and executing the
described task autonomously from start to finish, with no further interaction required. All inference
runs locally on consumer-grade hardware, no data leaves the device at any point, and the action se-
quence is generated by a deterministic automated planner that produces a minimal and reproducible
execution path.

Chapter 2

State of the Art

This chapter reviews the Artificial Intelligence (AI) foundations required to understand the proposed
system. It is organised around three complementary approaches: symbolic AI, which represents
knowledge explicitly and reasons through formal rules; sub-symbolic AI, which learns representa-
tions from data; and hybrid approaches that combine both families of methods. This distinction is
important because desktop automation requires formal action planning, language and visual percep-
tion, and a mechanism to connect abstract plans with real graphical interfaces.


2.1     Symbolic Artificial Intelligence

Symbolic AI began with early work such as the Physical Symbol System Hypothesis by Newell
and Simon [3]. It represents knowledge as explicit symbols manipulated through logical rules. In
this project, its most relevant branch is Automated Planning: the synthesis of action sequences that
transform an initial state of the world into a desired goal state. A planning system is characterised
by three interconnected components: (1) representation language used to model the world and its
actions, (2) search algorithm that navigates the state space; and (3) heuristic function that guides the
search efficiently.


2.1.1    Representation Languages

A knowledge representation language is a formal, symbolic system designed to encode structured
information about a domain in a way that is both human-readable and machine-interpretable. Such
languages define a syntax for expressing entities, relations, and constraints, along with a semantics
that supports automated reasoning, inference, and planning over the encoded knowledge.

   1. The Stanford Research Institute Problem Solver (STRIPS) [4] introduced one of the first for-
      mal languages for planning. A state is represented as a set of ground propositions, and an
      action is defined by preconditions that must hold before execution, delete effects that become
      false afterwards, and add effects that become true. This simple structure remains influential
      because it describes actions through explicit and inspectable state transitions.

      goal), enabling a single domain to be reused across many problem instances. A classical
      planning task can be defined as:

   3. Modern planners commonly compile PDDL into the Simplified Action Structures (SAS+)
      formalism [6]. Instead of binary propositions, SAS+ represents each world state as a vector
      of multi-valued variables. This compact representation exposes implicit constraints, reduces
      the branching factor, and enables mutex reasoning: the detection of facts that cannot be true at
      the same time. This is useful in GUI automation because many interface states are mutually
      exclusive, such as a window being both open and closed.


2.1.2     Heuristics

A heuristic is a function h(n) that estimates the cost of reaching a goal state from a given state n.
A heuristic is admissible if h(n) ≤ h∗ (n) for all n, meaning it never overestimates the true optimal
cost.
Delete-relaxation heuristics estimate goal distance by ignoring the delete effects of actions, which
simplifies the planning graph and makes the estimate tractable to compute. hFF [7] is the canonical
example: it extracts a relaxed plan from this simplified graph and uses its length as the heuristic
value. LM-cut [8] takes a different approach by identifying landmark cuts: sets of actions such that
every valid plan must include at least one action from each set. Because LM-cut is admissible, it




                                                                         COMPUTER SCIENCE DEGREE
is particularly suited for optimal planning. Landmark-based heuristics [9] estimate goal distance by
counting how many landmarks, i.e., facts or actions that must occur in every solution, remain to be
achieved.


2.1.3    Search Algorithms

Planning reduces to searching through a state space that can grow exponentially with the number
of variables. Breadth-First Search (BFS) guarantees optimality by expanding states level by level,
but is impractical for large spaces. Greedy Best-First Search prioritises states with the lowest h(n),
trading optimality for speed. A* [10] balances both by evaluating each state with:


                                        f (n) = g(n) + h(n)                                      (2.2)

where g(n) is the accumulated cost from the initial state and h(n) is the heuristic estimate of the
remaining cost. When h(n) is admissible, A* is guaranteed to find an optimal plan. Iterated search
[9] runs successive search passes with decreasing cost bounds, improving solution quality over time
without requiring a single optimal search from the start.
In the context of GUI automation, plan optimality matters because unnecessary actions increase
latency and create additional opportunities for visual or execution errors.


2.1.4    Classical Planners

Several state-of-the-art systems implement these ideas. FF [7] popularised delete-relaxation heuris-
tics for satisficing planning. LAMA [9] combines landmark-based heuristics with iterated search and
has performed strongly in International Planning Competitions. Fast Downward [11] is a modular,
open-source framework that translates PDDL into SAS+ and supports many search algorithms and
heuristics through a declarative configuration language. It has consistently ranked among the top
systems in planning competitions [12].
This project uses Fast Downward with the LM-cut heuristic because this configuration provides cost-
optimal and reproducible GUI automation plans. However, symbolic planning alone cannot perceive
the visual state of the desktop. This is the Symbol Grounding Problem [13]: the planner may know
that the next action is to click a specific icon, but it cannot determine where that icon appears on
screen. This limitation motivates the use of sub-symbolic models.


2.2     Sub-Symbolic Artificial Intelligence

Sub-symbolic AI does not rely on manually encoded rules. Instead, it learns numerical represen-
tations from data through the adjustment of model parameters. A neural network is a parametric
function composed of interconnected artificial neurons [14]. Each neuron receives numerical inputs,
applies learned weights and a non-linear activation function, and passes the result to subsequent neu-
rons. During training, optimisation algorithms adjust these weights so that the network maps inputs
to desired outputs. Stacking neurons into multiple layers forms a Deep Neural Network (DNN),
which can learn increasingly abstract patterns from raw input.

2.2.1     Neural Network Architectures

2.2.1.1   Convolutional Neural Networks (CNNs)

Convolutional Neural Networks (CNNs) [15] are neural architectures designed for data with a spa-
tial structure, especially images. Instead of connecting every input pixel to every neuron, CNNs use
convolutional filters that move across local regions of the input. This reduces the number of param-
eters and allows the model to learn visual patterns that are shared across different positions in the
image.
The first layers of a CNN usually learn simple visual features, such as edges, corners, colour transi-
tions, and small textures. Deeper layers combine these low-level features into increasingly abstract
representations, such as shapes, object parts, and complete objects. This hierarchical organisation
made CNNs especially influential in computer vision, where recognition often depends on combin-
ing local visual evidence into a broader interpretation of the scene.
Pooling operations are commonly used with convolutions to reduce the spatial resolution of inter-
mediate feature maps. This makes the representation more compact and gives the model a degree of
tolerance to small translations or distortions. As a result, a CNN can recognise that a visual element
is present even if it appears in a slightly different position, size, or visual context.
CNNs are relevant to Autopilot because desktop automation depends on visual perception. A system
that interacts with a graphical user interface must reason over screenshots, identify icons, buttons,
windows, and text regions, and relate those visual elements to possible actions. Even when the final
implementation relies on more recent vision-language models, the basic idea of extracting structured
visual features from images remains foundational.
In this Final Degree Project (FDP), CNNs therefore provide historical and conceptual context for
the visual components of the system. They explain how neural models can transform raw pixels
into useful visual representations, which is a necessary step before higher-level models can ground
natural language instructions in screen coordinates. This connection is important because Autopilot
must bridge the gap between what the user says and what is visually available on the Windows
desktop.


2.2.1.2   Recurrent Neural Networks (RNNs), Long Short-Term Memory (LSTMs), and Gated
          Recurrent Units (GRUs)

Recurrent Neural Networks (RNNs) are neural architectures designed for sequential data. Unlike
feed-forward networks, they maintain a hidden state that is updated at each timestep. This hidden
state acts as a memory of previous inputs, allowing the model to process sequences such as text,
speech, commands, or time-dependent observations.
The main advantage of RNNs is that they can represent temporal dependencies. In language and
speech, the meaning of a token or sound often depends on what came before it. For example, a
spoken command cannot be interpreted reliably by treating every word as independent; the order
of the words determines the intended action. This makes recurrent architectures a natural early
approach for speech recognition and natural language processing.
However, standard RNNs have difficulty learning long-range dependencies. As sequences become
longer, the training signal can become unstable, and information from earlier timesteps may be




                                                               COMPUTER SCIENCE DEGREE
lost. Long Short-Term Memory networks (LSTMs) [16] address this issue by introducing gates that
control which information is stored, forgotten, or exposed to the next timestep. This makes them
better suited to sequences where relevant information may appear far apart.
Gated Recurrent Units (GRUs) [17] provide a related recurrent architecture with a simpler gating
mechanism. They combine some of the memory and update operations used by LSTMs, reducing
the number of internal components while preserving the ability to model temporal context. GRUs
are often used when a recurrent model needs to capture sequential dependencies with lower compu-
tational complexity than a full LSTM.
These recurrent architectures are relevant to Autopilot because the system begins from a spoken nat-
ural language instruction and must preserve the structure of that instruction through transcription,
interpretation, and planning. Although the final pipeline uses more recent large models for com-
mand understanding and orchestration, RNNs, LSTMs, and GRUs establish the core idea that neural
systems can model ordered information rather than isolated inputs. This makes them an important
conceptual bridge between basic neural networks and the large sequence models discussed later.


2.2.2     Large Models

2.2.2.1   Transformers

Transformers [18] are neural architectures designed to process sequences through attention rather
than recurrence. Their central mechanism is self-attention, which allows each token in an input
sequence to compare itself with every other token and assign different levels of importance to them.
This means that the representation of a word, image patch, or audio segment can be computed
in relation to the surrounding context, rather than only from a fixed local window or a sequential
hidden state.
The Transformer architecture is built from stacked layers that combine self-attention with feed-
forward neural networks, residual connections, normalisation, and positional information. Since
self-attention itself does not encode order, positional encodings are added so that the model can
distinguish between different positions in a sequence. This design makes it possible to model both
local and long-range dependencies while still allowing many operations to be computed in parallel.
This parallelism is one of the main reasons Transformers enabled the current generation of large
models. Unlike recurrent models, which process tokens step by step, Transformers can process
entire sequences more efficiently during training. When trained on very large datasets and scaled to
billions of parameters, they learn flexible representations that can be adapted to language, speech,
vision, and multi-modal tasks. As a result, Transformers provide the architectural foundation for
many modern Speech-to-Text models, Vision-Language Models, and Large Language Models.


2.2.2.2   Speech-to-Text Models (STT)

Speech-to-Text (STT) models convert spoken audio into written text. Modern STT systems typically
transform an audio waveform into acoustic features and then map those features to a sequence of
text tokens. Whisper [19], for example, uses an encoder-decoder architecture trained at large scale
to produce robust transcriptions across languages, accents, and noisy conditions. In Autopilot, this
model family is necessary because the system begins with a spoken natural language instruction that




FINAL DEGREE PROJECT | Universidad Francisco de Vitoria                                           8
must be converted into text before it can be interpreted by the rest of the pipeline.
The quality of the STT stage directly affects all later components. If the transcription changes the
user’s intent, omits an important object, or introduces an incorrect word, the planning and execution
stages may receive the wrong task specification. For this reason, an STT model used in desktop
automation must be robust not only in general accuracy, but also in preserving task-relevant entities
such as application names, file names, commands, and UI labels. Local STT execution is also
relevant to the privacy goals of the Final Degree Project (FDP), because spoken instructions may
contain personal or sensitive information.


2.2.2.3   Vision-Language Models (VLMs)

Vision-Language Models (VLMs) combine visual and textual information in a shared reasoning
process. They usually include a visual encoder that represents images or screenshots and a language
component that interprets prompts, questions, or instructions. This allows the model to answer
questions about an image, describe visual content, or connect textual references to visual regions. For
GUI automation, their most important capability is visual grounding: mapping a textual description
of an interface element to its approximate position on the screen.
In Autopilot, VLMs act as the perceptual bridge between symbolic actions and the graphical desktop.
A symbolic planner can produce an action such as clicking a browser icon or selecting a menu option,
but it does not know where that object appears in the current screenshot. A VLM can evaluate
the screenshot, decide whether the requested element is visible, and provide coordinates or visual
confirmation. This makes VLMs essential for screen understanding, element localisation, and final
task verification.


2.2.2.4   Large Language Models (LLMs)

Large Language Models (LLMs) are Transformer-based models trained on large text corpora and
adapted to generate or interpret natural language. They can follow instructions, classify intent, rea-
son over multi-step tasks, and produce structured outputs such as JSON. These properties make them
useful for transforming a user’s free-form command into a more explicit computational representa-
tion, as well as for coordinating different components in an automation pipeline.
For this Final Degree Project (FDP), LLMs are especially important because they support flexible
interaction without requiring the user to memorise rigid commands. The same underlying model
family can be used to identify the intended task, extract arguments, interpret intermediate state, and
orchestrate calls to specialised agents. However, LLMs are probabilistic systems, so their outputs
must be constrained and checked when reliability is required. Autopilot addresses this by combining
LLM-based interpretation with a symbolic planning layer and dedicated verification components.
In this Final Degree Project (FDP), these model families provide the sub-symbolic capabilities re-
quired by Autopilot. STT models convert the user’s spoken command into text, LLMs interpret
the command and orchestrate the execution flow, and VLMs connect the symbolic plan to the vi-
sual state of the Windows desktop. Quantisation reduces model memory requirements, often with
limited accuracy degradation, making it feasible to run these components locally on consumer hard-
ware. Together, they allow the system to combine natural language interaction, visual perception,
and local execution while preserving the privacy-oriented goals of the Final Degree Project (FDP).

2.2.3    AI Agents and Orchestration Frameworks



An AI agent is a software entity that perceives an environment, reasons about the current state,
selects an action, and executes that action through available tools. This structure is usually described
as a perception–reasoning–action loop. The agent first receives information from the environment,
then interprets that information in relation to a goal, and finally produces an action that changes the
environment or advances the task.
In desktop automation, the environment is the graphical user interface of the operating system. Per-
ception can be implemented through screenshots, OCR, or visual models that identify interface el-
ements. Reasoning can be performed by an LLM, a symbolic planner, or a combination of both.
Actions are executed through tools such as mouse movement, clicking, typing, keyboard shortcuts,
file operations, or application-level commands. The result of each action can then be observed again,
creating a feedback loop between the agent and the desktop.
Agents are useful because they connect high-level goals with concrete operations. A user may
express a goal such as opening an application, locating a file, or completing a form, but the system
must decompose that goal into smaller executable steps. In this sense, an agent is not merely a
model that generates text; it is a controller that uses model outputs, tool calls, observations, and state
information to decide what should happen next.
For complex tasks, a single general-purpose agent can become difficult to control. It may need to in-
terpret language, inspect the screen, select tools, maintain execution state, recover from errors, and
verify the result at the same time. Multi-agent architectures address this by assigning specialised
responsibilities to different agents. An intention agent can classify the user’s request and extract
arguments; a planning or translation component can convert the request into an explicit action se-
quence; a vision agent can locate elements on screen; a manager agent can coordinate execution;
and a quality-assurance agent can verify whether the final state satisfies the user’s goal.
Orchestration is the mechanism that coordinates these specialised agents and determines the order
in which they are called. It defines how information flows between components, how intermediate
outputs are represented, and how the system reacts when a step succeeds or fails. In an automation
pipeline, orchestration is important because the output of one component often becomes the input of
the next one: a transcription becomes an interpreted intent, an intent becomes a plan, a plan becomes
a sequence of GUI actions, and the final screenshot becomes evidence for verification.
Many modern systems use orchestration frameworks to make this coordination explicit. CrewAI [20]
organises agents into roles, tasks, and crews, passing outputs from one task to the next. LangGraph
[21], built on the LangChain ecosystem, represents workflows as directed graphs with nodes, condi-
tional transitions, and shared state. These frameworks help modularise and inspect agent pipelines,
although they do not by themselves guarantee correct planning or execution.
In this Final Degree Project (FDP), the agent concept is used to structure Autopilot as a set of
specialised components rather than as a single monolithic model. The Intention Agent interprets
the spoken command once it has been transcribed, the Manager Agent coordinates the execution
flow, the visual agents connect symbolic actions to the screen state, and the QA Agent verifies task
completion. These roles are described here because they are used in later chapters to explain the
architecture, implementation, and evaluation of the system.

2.3     Combining Symbolic and Sub-Symbolic AI




Symbolic and sub-symbolic methods can be combined when a task requires both explicit struc-
ture and learned interpretation. Symbolic systems are useful when the problem can be represented
through rules, states, actions, constraints, or search spaces. Sub-symbolic systems are useful when
the input is noisy, ambiguous, or difficult to encode manually, such as natural language, speech, im-
ages, or learned value estimates. Hybrid approaches connect these capabilities by assigning different
parts of the problem to different methods, rather than forcing a single technique to solve the entire
task.
Language interfaces for symbolic planning. One common pattern is to use a learned language
model to translate an informal user request into a formal representation that a symbolic planner can
solve. LLM+P [22] follows this pattern by converting natural language planning problems into
Planning Domain Definition Language (PDDL), using a classical planner to obtain a correct or
optimal plan, and translating the result back into natural language. This illustrates how sub-symbolic
language understanding can be connected to symbolic planning without replacing the planner itself.
Grounding generated actions in feasibility constraints. A second pattern is to use learned models
to propose or interpret high-level actions, while another component checks whether those actions
are feasible in the environment. SayCan [23] combines large language models with learned robotic
affordances, so that the language model contributes semantic knowledge about the task while the
affordance model scores which actions the robot can actually execute. This prevents high-level
language reasoning from producing plans that are plausible in text but impossible for the embodied
system.
Search guided by learned models. A third pattern is to combine learned evaluation functions with
structured search. AlphaGo [24] combines deep neural networks with Monte Carlo tree search:
policy networks suggest promising moves, value networks estimate board positions, and tree search
explores possible future states. This example shows that neural models can guide a search process
without removing the need for explicit exploration over a structured state space.
Evolutionary search over neural architectures. Hybridisation can also occur in the opposite di-
rection: a symbolic or algorithmic search method can be used to design or optimise a sub-symbolic
model. Genetic CNN [25] applies a genetic algorithm to search over convolutional neural network
architectures. Candidate network structures are encoded, mutated, crossed over, trained, and se-
lected according to their validation performance. This demonstrates that evolutionary algorithms
can operate over deep neural networks and discover architectures that would be difficult to design
manually.
These examples show that combining symbolic and sub-symbolic AI is not a single fixed architec-
ture, but a set of design patterns. The connection may occur through translation between language
and formal planning, through feasibility checks, through learned guidance for search, or through
symbolic/evolutionary search over neural systems. In this Final Degree Project (FDP), this perspec-
tive motivates the separation between learned components for speech, language, and vision, and
explicit components for planning and execution control.

2.4     Related Work

Several existing systems address desktop automation through different architectural choices. They
can be compared along two axes: autonomy, meaning whether the system requires step-by-step
commands or accepts a single prompt, and locality, meaning whether processing remains on-device
or depends on cloud infrastructure.
Windows Voice Access [26] is a built-in Windows 11 accessibility feature that maps predefined
voice commands to actions such as clicking, typing, and opening applications. It is local and useful
for hands-free control, but it provides no planning layer: the user must issue each action individually
and therefore remains responsible for decomposing the task.
Claude Cowork [27] is a cloud-based AI assistant with computer-use capability. Given a single
natural-language prompt, it operates reactively by capturing a screenshot, selecting an action, execut-
ing it, and repeating the loop until completion. This enables autonomy but can produce non-optimal
paths, and screenshots and context are processed externally.
Gemini Computer Use [28] is a cloud-based computer-use API with a similar reactive design. It
supports autonomous screen capture in one mode and externally injected screenshots in another,
which affects the level of autonomy of the evaluated system. Like Claude Cowork, it relies on cloud
processing.
OpenClaw [29] is an open-source local system that exposes desktop control tools directly to a
general-purpose LLM. It accepts a single prompt and runs autonomously, but it has no dedicated
deterministic planning layer, so the model must reason about the full task, select tools, and recover
from errors inside a single unstructured loop.
These systems show the main trade-off in current desktop automation. Local tools preserve privacy
but often rely on fixed commands or lack formal planning, while cloud-based systems support flex-
ible natural language interaction but expose screen and task data to external services. The proposed
system is positioned between these approaches by combining local processing, spoken natural lan-
guage input, deterministic planning, and visual grounding. A detailed description of the competitors
and their evaluation setup is provided in Appendix A.

Objectives

3.1     Main Objective

The main goal of this project is to develop a fully autonomous desktop automation system that allows
users to operate a Windows computer through free-form spoken natural language. The system must
interpret a single voice request, plan and execute the required desktop actions through the graphical
interface, and verify task completion without further human intervention, while keeping the entire
processing pipeline on the local device.
Hypothesis: a Windows computer can be controlled autonomously from spoken natural language
by combining local speech transcription, language-based intent interpretation, automated planning,
visual desktop perception, and closed-loop verification. If these components are integrated into a
local pipeline, then common desktop tasks can be completed without manual input, fixed command
syntax, or external data transmission.


3.2     Specific Objectives

The following specific objectives use the SO convention and divide the main objective into six con-
crete targets aligned with the project presentation, while using the formal terminology required by
the review feedback. Each objective addresses a distinct requirement that the system must satisfy to
be considered a valid autonomous desktop automation solution.

   1. SO1: Data Sovereignty and Privacy. This objective requires the entire processing pipeline
      to run on the user’s own computer, without relying on external services, remote models, or
      cloud APIs. Voice recordings, screenshots, task descriptions, file names, and intermediate
      outputs must remain on the device at all times. This is important because desktop automation
      may involve sensitive personal information, and the system must remain usable even without
      internet access, third-party availability, or remote infrastructure.
   2. SO2: Robustness, Predictability, and Determinism in the Planning Layer. This objective
      requires the planning layer to produce predictable and deterministic action sequences from




                                                              COMPUTER SCIENCE DEGREE
      the interpreted user intention. The same or equivalent task descriptions should lead to the
      same valid plan, without missing, incorrect, or redundant actions. This objective is important
      because the planner acts as the bridge between uncertain language input and concrete desktop
      execution, so its behaviour must be explainable, inspectable, and stable across repeated runs.

   3. SO3: Closed-Loop Autonomy. This objective requires the system to execute the planned
      actions without further human input after the initial voice request has been received. Auton-
      omy must include closed-loop verification: the system has to observe the desktop state, detect
      whether each relevant step produced the expected effect, and decide whether the task has been
      completed. This is important because a system that performs actions but cannot verify their
      result cannot be considered reliable autonomous control.

   4. SO4: Benchmarking with Other Solutions. This objective requires the proposed system
      to be evaluated against other local and cloud-based desktop automation alternatives under
      comparable conditions. The comparison must consider task completion, execution reliability,
      number of actions, latency, and data exposure. This is important because the system is not
      only intended to work in isolation, but to demonstrate that a local neuro-symbolic approach
      can be competitive with existing solutions while preserving privacy.

   5. SO5: Spoken Natural Language User Interface (Hands-Free Interaction). This objective
      defines the system as a spoken natural language user interface for hands-free interaction. The
      user must be able to describe a task through a single free-form voice prompt, without using a
      keyboard, mouse, touch input, or a fixed command vocabulary. This is important because the
      system should adapt to natural user phrasing instead of forcing users to learn rigid command
      syntax before they can operate the computer.

   6. SO6: Graphical User Interface for Desktop Automation. This objective requires the sys-
      tem to include a graphical interface that allows a non-technical user to provide the initial voice
      request and observe the automation process without interacting with technical tools such as
      terminals. It is placed after the autonomy, planning, benchmarking, and input objectives be-
      cause the interface depends on the underlying system being able to interpret, plan, execute,
      and verify tasks. This is important because the final system should be usable as an application,
      not only as an internal prototype.

4.2     Methods

Automated planning. Task planning will be performed using the Planning Domain Definition Lan-
guage (PDDL), separating the representation language from the planner, the search algorithm, and
the heuristic. The PDDL domain file defines the available GUI actions as operators with precon-
ditions and effects, while the PDDL problem file specifies the initial desktop state and the goal
conditions for each supported task. Fast Downward then solves each problem instance using the A*
search algorithm with the LM-cut heuristic. LM-cut identifies landmarks, facts that must become
true in any valid plan, and computes a minimum cost through them, providing an admissible lower
bound that guarantees the generated plan is optimal in terms of number of steps.
Visual perception and verification. Screen element detection will be performed by a Vision-
Language Model that receives a screenshot and a textual description of a target element and returns
a binary YES/NO verdict on whether the element is currently visible. Coordinate grounding will
be handled by the same model family in a dedicated role, returning normalised coordinates within a
1000x1000 resolution space that are then mapped to the actual screen resolution. Task completion
verification will also rely on the VLM, receiving a final screenshot and confirming whether the goal
state has been reached.
Language understanding. Intent classification will be handled by a local LLM that maps the tran-
scribed voice input to a structured JSON object containing the task template identifier and its required
arguments.
Multi-modal orchestration. Pipeline orchestration will also be handled by the same LLM family
in a dedicated Manager role, which receives the translated action list and dispatches each specialised
agent. The resulting interaction is multi-modal because the system combines spoken natural lan-
guage, visual screen interpretation, automated plans, and GUI actions inside the same execution
loop.
Evaluation protocol. System performance will be assessed across seven task templates, each ex-
ecuted over three independent runs starting from a clean desktop state with no applications pre-
loaded, yielding 21 total evaluation runs. Eleven metrics will be measured across four categories:
performance (task success rate, step accuracy, end-to-end latency), reliability (planning error rate,
tool hallucination rate, visual hallucination rate, total error rate), consistency (standard deviation of
steps and latency), and privacy (data exposure level and total steps). Autopilot will be benchmarked
against four alternative systems: Windows Voice Access, Claude Cowork, OpenClaw, and Gemini
Computer Use, all evaluated under identical conditions on the same hardware, task templates, and
metric set.



4.3     Methodology

The project follows a Lean Research methodology inspired by the Lean Startup approach. Instead
of assuming the final architecture from the beginning, the work is organised around short valida-
tion cycles in which each technical decision is treated as a hypothesis, tested through a concrete
experiment, and accepted or revised according to the evidence obtained. This methodology is ap-
propriate for Autopilot because the project combines uncertain components, such as local LLMs,
VLMs, desktop automation tools, and automated planning, whose behaviour can only be assessed




                                                                 COMPUTER SCIENCE DEGREE
reliably through empirical testing on the target hardware.
Hypothesis. Each development cycle begins with a technical assumption linked to one of the project
objectives. Examples include the assumption that local models can provide sufficient transcription,
reasoning, and visual grounding accuracy; that automated planning can produce reproducible desk-
top action sequences; or that a multi-agent pipeline can recover from intermediate GUI failures.
These hypotheses define what needs to be validated before the system can progress to the next ar-
chitectural decision.
Experiment. Each hypothesis is tested through a bounded experiment with a clear setup, input
conditions, and success criteria. Experiments include model benchmarking, planner validation with
PDDL domain and problem files, isolated agent tests, end-to-end task executions, and comparisons
against alternative systems. This keeps development grounded in observable behaviour rather than
in expected model capabilities.
Evidence. The outcome of each experiment is converted into evidence through quantitative metrics,
qualitative inspection, and failure analysis. Successful results support the current design decision,
while weak or inconsistent results trigger a redesign, model replacement, prompt revision, or archi-
tectural adjustment. The final system is therefore the result of repeated Hypothesis–Experiment–
Evidence cycles rather than a single linear implementation plan.

4.5     Constraints and Limitations

This section distinguishes between constraints and limitations. Constraints are design decisions
deliberately imposed on the project, while limitations are boundaries discovered during development
or capabilities that the current system does not provide.


4.5.1    Constraints

Local-only execution. No component of the pipeline may invoke an external API or transmit voice
recordings, screenshots, task descriptions, file names, or intermediate outputs to a cloud service.
All inference, planning, and execution must be performable with no internet access. This constraint
directly supports SO1, because privacy and data sovereignty are core objectives of the project.
Operating system. The system targets Windows 11 exclusively. All GUI automation relies on the
Windows graphical interface, and portability to other operating systems is out of scope.
Hands-free interaction. The user must be able to start the automation process through a spoken
natural language prompt, without requiring keyboard, mouse, or terminal interaction. This constraint
supports SO5 and also conditions SO6, since the GUI must expose the system as a usable voice-based
application rather than as a developer-only prototype.
Evaluation comparability. Autopilot and the competitor systems must be evaluated under the same
hardware, task templates, and metric set whenever possible. This constraint supports SO4 by making
the comparative benchmark meaningful and reducing experimental bias.


4.5.2    Limitations

Limited GPU Memory. The development laptop provides 7.71 GB of available VRAM. This hard-
ware limitation restricts the size of the local models that can be executed and forces the pipeline to




                                                               COMPUTER SCIENCE DEGREE
load models sequentially rather than keeping all models resident in GPU memory at the same time.
It mainly impacts SO1, SO3, and SO4, because privacy-preserving local execution must remain
feasible without exceeding consumer-level hardware resources.
Task template coverage. The system operates on a predefined set of PDDL task templates. Tasks
outside this set cannot be planned by the automated planning layer without authoring a new domain
and problem pair. This limitation impacts SO2 and SO3, since determinism and autonomy are
guaranteed only within the supported task space.
End-to-end latency. Every task execution must complete within 300 seconds from voice input to
verified completion on the target hardware. Runs exceeding this threshold are counted as failures
regardless of the desktop state at timeout. This limitation affects SO3 and SO4 because slow local
inference may reduce autonomous usability and comparative performance.
Application and interface variability. GUI automation depends on the visual state of Windows
applications, which may change due to screen resolution, interface updates, unexpected pop-ups,
or non-deterministic loading times. This limitation affects SO3 and SO6, because the system must
observe and react to desktop state changes but cannot control every external interface condition.

Technical Development

Autopilot is a fully autonomous desktop automation system for Windows, designed to let users
operate a computer using only their voice. The system accepts a single spoken natural language
command and executes the described task on the desktop without any further human interaction.
Its architecture combines deterministic automated planning with local neural perception, forming a
neuro-symbolic system where each component has a non-overlapping role.
The system is structured in three conceptual stages. In the first stage, the user’s voice input is
transcribed locally and classified into a structured intent with its relevant arguments. In the second
stage, a symbolic planner generates the optimal sequence of GUI actions required to reach the goal
state from the current desktop state. In the third stage, a set of specialised agents executes each step
by perceiving the screen visually and interacting with graphical interface elements through standard
mouse and keyboard actions, ending with a verification step that confirms task completion without
human review.
This chapter describes the system design and specifies the functional and non-functional require-
ments. This requirements section catalogues all identified functional and non-functional require-
ments using a structured attribute format.

5.1.1     Description of functional features

5.1.1.1   System Components

At a functional level, Autopilot is organised around a local speech interface, a local model runtime,
an agent-based orchestration layer, a symbolic planning layer, a GUI execution layer, and a final
verification stage. The speech interface uses Whisper to convert the user’s spoken command into
text. All language and vision model inference is managed by Ollama, which loads and unloads
models from VRAM on demand so that no more than one model is resident in memory at the same
time. This sequential loading strategy keeps peak VRAM usage within 8 GB and makes the system
viable on consumer-grade hardware.

generate the plan, translate that plan into executable operations, execute GUI actions, and verify the
final result. This design keeps each responsibility separated while still allowing the Manager Agent
to decide which component should be invoked at each moment of the run.

Write a Note is the simplest template and does not require the Vision Agent, since no coordinate

the Vision Agent identifies the folder or file icon on screen so that the Executor can click it.

introduction in the open document”, the Intention Agent extracts the target text and the file name.

action that triggers the application’s Find tool. The Vision Agent is used to interact with the Find
toolbar.

navigate, and finally paste. The Vision Agent is used at each navigation step and to locate the file
before copying.


5.1.1.3   Agents

The system uses specialised agents and code-based components with agent-like responsibilities.
Manager Agent. The Manager Agent is the central orchestrator. Before a plan exists, its prompt
defines the initial sequence of calls: it first sends the transcribed command to the Intention Agent,
then asks the Scout Agent to inspect the current screen, then invokes the Planner Agent, and finally
calls the PDDL Translator Agent. Once the translated plan is available, the Manager uses it as the
execution guide and decides which agent or tool must be called for each step. It has access to all
agents, monitors their outputs, and can repeat, skip, or replace a step when the observed desktop
state requires it.
Intention Agent. The Intention Agent receives the user’s transcribed command and chooses one
of the seven available task templates. It also extracts the arguments required by that template, such
as file names, folder paths, text content, formatting options, or target applications. Its output is a
structured representation of the selected template and its parameters, which defines the final goal
that the rest of the system must satisfy.
Scout Agent. The Scout Agent is responsible for interpreting the current desktop state from screen-
shots. It is used in two different moments of the execution. Before planning, it receives a template-
specific prompt that asks only for the information relevant to the selected task, instead of requesting
a full description of the entire screen. This allows the system to start from different desktop states
and reuse the current context, for example when the required application is already open. During
execution, the Scout receives a step-specific prompt and checks whether the required item is visi-
ble on screen. In this second mode, it returns a YES or NO answer that determines whether visual
grounding can be performed directly or whether a fallback action is required.
Planner Agent. The Planner Agent receives the final goal selected by the Intention Agent and
the current screen state reported by the Scout Agent. It uses the corresponding PDDL domain and
problem files, together with Fast Downward, to compute the sequence of actions needed to reach the
goal. Its output is the raw symbolic plan produced by the planner.
PDDL Translator Agent. The PDDL Translator Agent converts the raw planner output into a




FINAL DEGREE PROJECT | Universidad Francisco de Vitoria                                             26
Python dictionary containing the ordered executable steps, their target objects, and the information
needed by the Manager Agent to dispatch the correct agent or tool.
Vision Agent. When the Scout Agent confirms that a target item is visible, the Vision Agent receives
the same step-specific prompt and estimates the item’s coordinates in a normalised 1000x1000 res-
olution space. These coordinates are later mapped to the real screen resolution before execution.
Executor Agent. If the Scout returns NO, the Manager Agent calls the Executor Agent in fallback
mode. In this case, the Executor receives the objective and the target type, such as an application,
folder, or text element, and performs the necessary recovery actions to reach the expected state. In
normal execution mode, the Executor performs GUI actions through pyautogui, including writing
text, clicking, double-clicking, and sending hotkeys. It returns a SUCCESS status when the action
has been executed.
QA Agent. The QA Agent is invoked after the planned actions have been completed. It receives
a custom verification prompt and a screenshot of the final desktop state. Its output is a YES or
NO verdict, together with a brief explanation of whether the requested goal appears to have been
achieved.

Experiments

6.1       Quantitative Evaluation

All experiments were conducted on the same machine: an OMEN Gaming Laptop 16 with an AMD
Ryzen AI 7 350 @ 2 GHz, an NVIDIA RTX 5070 Laptop GPU (7.71 GB VRAM), 32 GB RAM,
running Windows 11 Home (25H2) and always plugged in using official charger. Although as it will
be seen, this setup over compensates for the need to run these models, using quantization techniques.
Cloud-based systems were evaluated over the same Wi-Fi connection to ensure consistent network
conditions.


6.1.1     System Evaluation

6.1.1.1   VLM Selection

The three VLM roles in Autopilot (Scout, Vision, and QA) share the same underlying model, but im-
pose different objectives. Scout and QA tasks can be fulfilled by most VLMs, as they are reasonably
capable at OCR. However, the Vision Agent presents a different challenge: it must return precise
screen coordinates. This visual grounding capability is not common across VLMs, and therefore it
was used as the primary criterion for model selection.
The evaluation setup follows the same hardware and software configuration declared in Section 4.1,
with the same validation methods defined in Section 3.3. The only difference is that the full pipeline
is not executed, but only the VLM model, called directly with the specific prompt for each template,
meaning that timing and VRAM usage reflect exclusively the VLM inference stage.
Six candidate models were evaluated across three task templates (Write a Note, Search and Open
File, and Change Text Format in Word), all of which require identifying icons and text on screen.
Each candidate is characterised by the number of parameters (Params), indicating the model size,
and the quantisation level (Quant.), where INT4 refers to 4-bit integer quantisation, a compression
technique that reduces memory usage at the cost of a minor precision loss. The metrics used are M-
01 Task Success Rate (TSR), defined as the percentage of runs where the model correctly identified

input and return the coordinates. Average VRAM usage is also reported, as it is a key factor in the
final model selection. Although more models were tested, only the INT4 quantised versions are
presented, as they were the most competitive across all dimensions.

7.1     AI-Based Systems Ethical Impact

The rapid advancements in artificial intelligence systems have raised a new debate on its ethical
implications. Traditionally, software programs execute explicit and deterministic instruction, which
are given and controlled by a human. Also, the same input always gave the same output, but if a
misbehaviour occurred, one could always traceback to a specific block of code. However, agentic
systems change the current paradigm, they can interpret natural language, reason over context and
plan a sequence of actions accordingly. They can interact with the real world on behalf of the user
or fully autonomously, with the added disadvantage of making it very difficult the entire thought
process it had on why doing certain actions. These AI models are starting to shift from tools to
operators.
This shift applies particularly to desktop automation, where an agent can interact with the graphical
interface and access everything visible on screen, this means sensitive data can be manipulated in
the worse case scenario. Furthermore, the actions taken might be irreversible, such as deleting from
the recycling bin a file. Therefore, a misinterpreted command does not only return a wrong answer
but might expose confidential data about the user. As seen the ethical stakes are considerably higher
than a regression model.
To address these concerns, several legal frameworks regulate the development and use of AI systems
of this kind.


    • General Data Protection Regulation (GDPR, Regulation (EU) 2016/679) [30]: The GDPR
      governs the processing of personal data in the EU. Its Article 25 introduces privacy by design
      and by default, requiring data protection to be embedded into a system’s architecture from the
      beginning.




                                                              COMPUTER SCIENCE DEGREE
    • Spanish Organic Law on Data Protection (LOPDGDD, Ley Orgánica 3/2018) [31]: The
      LOPDGDD is the national transposition of the GDPR into Spanish law. It reinforces the same
      principles of data minimisation, purpose limitation, and privacy by design, and is directly
      applicable given that Spain is the primary development and deployment context of this project.

    • European Artificial Intelligence Act [32]: This law aims to regulate the development and
      use of AI systems, ensuring that they are safe, transparent, and respectful of fundamental
      rights. It classifies AI applications into different risk levels and establishes strict requirements
      for high-risk systems, with the purpose of guaranteeing that they are used in a fair and ethical
      manner.



7.2     Ethical Dimensions Descriptions

In order to assess the ethical implications of this project, an ethical framework is needed, that is, a
structured set of principles used to evaluate whether an AI system aligns with broadly accepted val-
ues such as fairness, safety, privacy, and accountability. Among the available frameworks, Google’s
AI Principles [1] were selected as the most suitable for this analysis. They are structured around
seven concrete criteria that map directly onto the design decisions made throughout this project.
Their focus on privacy, safety, accountability and bias makes them particularly relevant for a sys-
tem that executes autonomous actions on a user’s machine, handles sensitive screen data, and runs
entirely on local hardware. Unlike other more abstract ethical guidelines, Google’s Principles were
designed with real product development in mind and address the complete lifecycle of an AI system,
making them the most suitable framework for the ethical analysis of a functional system like this
one.
Furthermore, given that this project is built around agentic systems, the analysis of the safety prin-
ciple is complemented by Google’s Secure AI Framework (SAIF) [2], a framework specifically de-
signed to address the security risks of AI systems, while its objective is very broad, it targets agentic
systems too. The SAIF identifies two primary risks in this context, Sensitive Data Disclosure and
Rogue Actions. These are the seven different dimensions that have been evaluated using Google’s
AI Principles, with a specific focus on how they apply to this system:

   1. Be Socially Beneficial. AI systems are to provide a tangible value to the users and society,
      while still minimising potential harms. This goes beyond functionality, including who is the
      end beneficiary, who is excluded from the target audience and what is the broader impact of
      the system. In this project, this principle translates into evaluating what societal problem this
      system aims to solve and how effectively it does so.

   2. Avoid Creating or Reinforcing Unfair Bias. AI systems can introduce bias in many ways,
      due to the data they were trained on. In the context of autonomous agents, bias can lead to
      an inconsistent behaviour, a misinterpretation of the user intent or to make certain actions that
      do not have the user as the final beneficiary, lacking transparency in the system. Here for this
      principle, it should be evaluated the steps that have been taken to ensure the system is fair and
      inclusive.

   3. Be Built and Tested for Safety. Safety in AI systems refer to the ability to operate accordingly
      to the user intent without causing any harm or disruption, especially in systems that interact




FINAL DEGREE PROJECT | Universidad Francisco de Vitoria                                                52
      with the real world. In desktop automation, this is crucial, where a misclick can result in
      irreversible changes in the user’s environment. This principle translates into evaluating how
      safety has been prioritised in the design and development of the system.
   4. Be Accountable to People. In this principle, accountability refers the ability to understand,
      audit and be responsible for the decisions made by the AI system. This in autonomous agents
      is especially important, where the system can act on behalf the user without necessarily ex-
      plaining all the step-by-step reasoning. In this project, this principle translates into evaluating
      how the system provides transparency and user control.
   5. Incorporate Privacy Design Principles. The term privacy by design refers to ensure that
      privacy should be built in the system from the ground up, rather than being added afterwards
      once is completed. In the context of AI systems that interact with the user’s desktop, this is
      particularly relevant since the system has complete access to sensitive information, such as
      personal files, and the content visible in the screen. Therefore, the key answer to this principle
      is to reflect on how this system protects user data and privacy.
   6. Uphold High Standards of Scientific Excellence. When developing systems in AI research,
      it is important that they comply with privacy first and security first rules, however, it is impor-
      tant that these systems are grounded in rigorous research, empirical evaluation and transparent
      methodology. This implies that any claim about the system’s capabilities should be backed by
      evidence and should be justified through scientific reasoning.
   7. Be Made Available for Uses that Accord with These Principles. This principle refers to
      the responsibility of ensuring that an AI system is only made available for uses that align with
      ethical guidelines. This prevents it from being reused for malicious or unintended intents,
      therefore the final applications of this system should be outlined accordingly.

Conclusions

9.1     General Conclusions

This project set out to answer whether a Windows desktop can be controlled autonomously from
a single spoken natural language instruction while keeping the full execution pipeline on the user’s
own device. The answer obtained through the implementation and evaluation of Autopilot is positive
within the task scope defined for this work. The final system can transcribe a spoken request, extract
the user’s intention, generate a deterministic PDDL plan, ground that plan in the graphical interface
through local vision-language models, execute the required actions, and verify the final state without
additional human intervention.
The main contribution of the project is the integration of local neural models with automated plan-
ning in a practical desktop automation pipeline. The results show that neither a purely command-
based approach nor a purely reactive LLM agent is sufficient to satisfy all the requirements addressed
in this report. Command-based systems such as Windows Voice Access can be fast and reliable, but
they require the user to decompose the task manually. Reactive cloud systems can accept open nat-
ural language, but they expose screenshots and task context to external services and may produce
inconsistent action sequences. Fully local LLM-based systems preserve privacy, but the evaluation
showed that tool access alone does not guarantee reliable automation. Autopilot demonstrates that
a neuro-symbolic architecture can reduce these weaknesses by assigning each responsibility to the
component best suited for it: language models interpret and orchestrate, vision-language models
perceive the screen, and the symbolic planner generates the action structure.
The experimental evaluation supports this conclusion. Across 21 runs covering seven task tem-
plates, Autopilot achieved a 100% task success rate, zero planning errors, zero tool hallucinations,
zero data exposure, and a deterministic step structure. In the autonomous-system comparison, it
matched Claude Cowork in task success while avoiding the data exposure of cloud-based systems
and reducing planning errors. In the fully local comparison, it clearly outperformed OpenClaw,
which did not complete any evaluated task under the same conditions. These results indicate that the
architecture, rather than only the choice of models or tools, is the decisive factor behind the system’s
reliability.
At the same time, the project also identifies important limitations. The system is currently restricted




FINAL DEGREE PROJECT | Universidad Francisco de Vitoria                                              60
to seven predefined PDDL task templates, so its determinism and reliability apply only inside that
controlled task space. End-to-end latency remains high compared with command-based interaction,
with an average of 111.83 seconds, mainly because local model inference and sequential orches-
tration are computationally expensive. Visual verification also remains imperfect: the QA Agent
reported success in 18 of 21 runs, with the remaining errors caused by visual judgement limita-
tions rather than actual task failure. These limitations do not invalidate the central hypothesis, but
they show that local autonomous desktop automation is still a constrained and engineering-sensitive
problem.
The qualitative study reinforces this balanced result. Participants perceived the system positively in
terms of error recovery, behaviour, privacy, and accessibility, and all user-study tasks were completed
successfully. However, daily-use likelihood and preference over alternatives were lower, mostly be-
cause of latency, transcription issues, and the limited number of supported templates. This suggests
that Autopilot is already a strong proof of concept for private and accessible desktop automation, but
not yet a general-purpose replacement for all forms of computer interaction.
From an ethical and social perspective, the project confirms the value of designing autonomous
agents with privacy, auditability, and limited action scope from the beginning. Running all infer-
ence locally directly addresses data sovereignty concerns, while PDDL planning makes the intended
action sequence inspectable before execution. The controlled template set also reduces the risk of
arbitrary or harmful actions. The main ethical weakness identified is accountability, since the current
system does not require explicit user confirmation before executing a plan. Overall, Autopilot shows
that autonomy and privacy do not have to be treated as opposing goals, provided that the system
architecture is designed around both from the start.
In conclusion, Autopilot validates the feasibility of a local, spoken, neuro-symbolic desktop automa-
tion system on consumer hardware. The project demonstrates that combining local LLMs, VLMs,
speech recognition, deterministic planning, and GUI execution can produce a system that is au-
tonomous, private, explainable, and empirically competitive within a defined task space. Its results
are especially relevant for accessibility and privacy-sensitive contexts, where cloud-based automa-
tion or step-by-step command systems are not fully satisfactory.




9.2     Conclusions regarding Project Objectives

The main objective of the project was to develop a fully autonomous desktop automation system for
Windows that operates from free-form spoken natural language, executes tasks through the graphical
interface, verifies completion, and keeps all processing local. This objective was achieved within the
seven supported task templates. The system completed all 21 evaluated runs successfully, worked
from spoken input, required no further human intervention after the initial prompt, and transmitted
no data outside the device.
SO1: Data Sovereignty and Privacy. This objective was fully achieved. The complete pipeline
runs locally, including speech transcription, language understanding, visual perception, planning,
orchestration, execution, and verification. The comparative evaluation assigns Autopilot a data ex-
posure level of 0, in contrast with cloud-based alternatives such as Claude Cowork and Gemini
Computer Use, both of which expose screenshots and task context externally. This confirms that the
system satisfies the privacy-by-design requirement established at the beginning of the project.




                                                                COMPUTER SCIENCE DEGREE
SO2: Robustness, Predictability, and Determinism in the Planning Layer. This objective was
also achieved. The PDDL planning layer produced deterministic plans with a planning error rate
of 0 and a standard deviation of steps of 0. The use of Fast Downward and explicit task templates
made the generated action sequences inspectable, reproducible, and free from missing or redundant
planning actions in the evaluated scenarios. The main limitation is that this guarantee only applies
to the predefined PDDL domains, not to arbitrary desktop tasks outside the supported task set.
SO3: Closed-Loop Autonomy. This objective was achieved for the evaluated scope. After the
initial spoken command, Autopilot executed each task without additional keyboard, mouse, touch,
or voice input from the evaluator. The system used Scout, Vision, Executor, Manager, and QA agents
to observe the desktop, act on the GUI, recover from intermediate states, and verify the result. The
acceptance criterion of at least 19 successful runs out of 21 was exceeded, with 21 successful task
completions. All runs stayed below the 300-second threshold, although the average latency of 111.83
seconds shows that speed remains one of the clearest limitations of the current implementation.
SO4: Benchmarking with Other Solutions. This objective was achieved through a comparative
evaluation against Windows Voice Access, OpenClaw, Claude Cowork, Gemini Computer Use, and
Gemini Computer Use with external screenshot injection. The benchmark used the same seven
task templates, three runs per template, and a common metric set covering success rate, latency,
error rates, consistency, steps, and data exposure. Autopilot was the strongest system among fully
autonomous and fully local alternatives, and it was the only evaluated system to combine 100% task
success, zero planning errors, deterministic step structure, and zero data exposure.
SO5: Spoken Natural Language User Interface (Hands-Free Interaction). This objective was
achieved. Every evaluated Autopilot run began from a free-form spoken prompt, transcribed locally
through Whisper and interpreted by the Intention Agent. The user did not need to learn a fixed
command vocabulary or manually decompose the task into interface-level instructions. The quali-
tative study also confirmed that participants could initiate tasks naturally by voice, although some
transcription errors were observed and should be considered a current usability limitation.
SO6: Graphical User Interface for Desktop Automation. This objective was only partially
achieved. The implemented interface is useful as a demonstration layer because it allows the eval-
uator to trigger the system, observe the automation process, and show that the underlying pipeline
works without requiring direct terminal interaction. However, it should not be considered a complete
end-user application. The GUI was not designed or validated for daily use by non-technical users,
and it lacks the polish, robustness, feedback mechanisms, and interaction design that would be re-
quired for a real accessibility-oriented product. Therefore, the objective was achieved as a functional
prototype, but not as a fully finished user-facing interface.
Overall, five of the six specific objectives were satisfied within the defined scope of the project,
while the graphical interface objective was only partially completed. The strongest achievements
are privacy preservation, deterministic planning, autonomous task completion, and empirical com-
petitiveness against other systems. The main remaining weaknesses are latency, limited task cover-
age, speech transcription robustness, the maturity of final-state visual verification, and the lack of a
production-ready interface for real daily use.

9.3     Next Steps

The first next step is to fine-tune Gemma4 for the specific orchestration and intent-classification tasks
required by Autopilot. The current system uses a general-purpose local model, which is flexible but
introduces latency and occasional inefficiency in the Manager and Intention stages. A task-specific
fine-tuned model could reduce execution time, make agent dispatching more precise, and improve
consistency across repeated runs.
The second improvement is to integrate the Whisper speech-to-text output more directly with the
Intention Agent. At the moment, speech transcription and intent extraction are treated as separate
stages, which increases the computational cost of the pipeline. A tighter integration between the
STT component and the intent-classification step could reduce duplicated processing and make the
initial phase of the system faster.
The third next step is to evaluate the system with physically impaired users. The current qualitative
study provides useful feedback from general participants, but the main social motivation of the
project is accessibility for users with motor difficulties. Testing with this target group would make
it possible to assess whether Autopilot addresses real accessibility needs, which interaction barriers
remain, and which tasks would be most valuable in daily use.
The final next step is to design and implement a custom GUI for end users. The current interface
demonstrates the technical feasibility of the system, but it is not a complete product interface. A fu-
ture version should include a more accessible and polished design, clearer execution feedback, error
messages, status indicators, configuration options, and interaction flows suitable for non-technical
users who may rely on the system regularly.

Appendix A

Competitor Systems

This appendix provides detailed descriptions of the desktop automation systems evaluated against
Autopilot in Chapter 6. Each system is described in terms of its architecture, operational require-
ments, and relevant limitations observed during evaluation.


A.1      Windows Voice Access

Windows Voice Access is a built-in accessibility feature in Windows 11 that allows users to control
their computer using voice commands. It provides up to 80 commands for various actions, such as
opening applications, clicking buttons and typing, which are the core actions required to complete
the task templates. The system was tested with the laptop’s built-in microphone, and the command
execution was verified through audio recordings to ensure that the correct commands were issued
for each step in the task templates. Here the main disadvantage of this system is that the user is the
planner and WVA is the executor, meaning that the user cannot give a full prompt at the beginning of
the task, but must give commands step by step, which fails to meet the requirement of a single prompt
and fully autonomous execution. Moreover, the user must be familiar with the specific commands
and their syntax, which can be a barrier for non-technical users.


A.2      Claude Cowork

Claude Cowork is a collaborative cloud based AI system developed by Anthropic, designed to assist
users in various tasks through natural language interactions. One of its functionalities (still in Beta) is
computer use. It allows the user to give a single prompt describing the task they want to accomplish,
and then the system takes care of executing it, using the GUI, terminal or any available tool. The
system provides a visible thought process, where it explains the steps it is taking to complete the
task, which allows for a detailed evaluation of its performance and the reasoning behind its actions.
Claude Cowork’s main objective is to serve as an accessible alternative to Claude Code for non-
technical users, providing a dedicated Windows application with a more intuitive interface. However,
during computer use sessions, the system uses other tools, such as opening the terminal or calling




FINAL DEGREE PROJECT | Universidad Francisco de Vitoria                                                 64
the Windows Run dialog (Win+R), actions that despite being effective, they may generate distrust in
users who are not familiar.
Unlike Autopilot’s PDDL architecture, Claude Cowork operates reactively, meaning that it captures
a screenshot, decides an action, executes it, and repeats the cycle until the goal is completed, with
no first planning stage. This approach is great for simple tasks, which are very straightforward and
do not require any long and complex reasoning, however, as evidenced in the recorded runs and later
reflected in the comparative metrics, it also leads to non-optimal execution paths in more complex
tasks, where the system becomes repetitive after reaching dead ends or fails to identify the most
direct route to the objective.
A recurring pattern observed across templates is that Claude Cowork opens a target file or window
and immediately minimises it, as documented in Run 3 of the Search & Open template, meaning
that in the next step, Claude thinks the task was not completed, despite being completed. Although,
the system’s fast actions allow it to recover and complete most tasks within a competitive time.


A.3      OpenClaw

OpenClaw is an open-source desktop automation system designed for the model to use various tools
at hand to comply with user demands, without providing a dedicated GUI. It was evaluated using
Gemma4 E4B INT4 and Qwen3.5 8B INT4 across two tool integration approaches: skills and MCPs,
tested independently.
Two skills were evaluated: Desktop Control, which covers mouse, keyboard, screen capture, and
clipboard management via OpenCV, and Windows UI Automation, which automates Windows GUI
interactions through native APIs and PowerShell. Two MCPs were also tested: PyAutoGUI MCP,
which exposes mouse, keyboard, and screen control as model-callable tools, and Windows-MCP by
CursorTouch, which combines PyAutoGUI with the Windows UIAutomation framework for native
element interaction without computer vision. None of these configurations was sufficient for the
model to reliably plan and execute the task templates.


A.4      Gemini Computer Use

Gemini Computer Use (Gemini CU) is a cloud-based desktop automation system developed by
Google, that allows users to control the desktop through natural language commands. However,
it currently only offers an API with no dedicated user interface, which makes it less accessible for
non-technical users. Thus, a Python script had to be developed in order to interact with the model.
Both variants used gemini-3-flash-preview as the underlying model.
Two variants were implemented and evaluated, due to the specific recommendation in the Google
documentation, which states it is better for the developer to provide a screenshot after each action,
rather than leaving the model to decide when to capture the screen. Although, this goes against
the core principle of fully autonomous execution, therefore, both approaches were implemented and
evaluated to determine the best integration pattern for this system.
In the first variant, Gemini CU, take_screenshot is exposed as one of the available tools, the model
decides autonomously when to observe the screen, calling it only when it deems necessary. In the




                                                              COMPUTER SCIENCE DEGREE
second variant, Gemini Screenshot (Gemini SS), the screenshot tool is removed entirely and the
orchestration script automatically captures and injects a screenshot into the conversation after every
action, ensuring the model always has an up-to-date view of the desktop state before its next decision.
A significant practical limitation observed throughout both evaluations was API availability. Out of
42 total runs, 22 had to be repeated due to the API returning resource exhaustion errors, indicating
that the service was under heavy load. This instability introduces a substantial reliability concern for
any deployment that depends on consistent response times.
